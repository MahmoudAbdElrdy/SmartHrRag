# شرح مشروع Smart HR RAG

## الصورة العامة

المشروع تطبيق واحد مقسم إلى طبقات، ويستخدم أفكار Clean Architecture وPorts and Adapters:

- Domain: نماذج المستندات ومقاطع السياسات.
- Application: حالات الاستخدام، مثل إدخال السياسة والبحث والإجابة، مع واجهات للتخزين وOllama.
- Infrastructure: تطبيق الواجهات باستخدام EF Core وSQL Server وعميل Ollama واستخراج النص من PDF وDOCX.
- API: يستقبل HTTP requests ويربطها بحالات الاستخدام.
- Angular: واجهة منفصلة تستدعي الـAPI من خلال proxy أثناء التطوير.

الـAPI والبنية التحتية يعتمدان على Application وDomain. منطق Application لا يعتمد مباشرة على SQL Server أو Ollama.

## ماذا يحدث عند إضافة سياسة؟

1. الواجهة ترسل الاسم والنص إلى POST /api/policies/text.
2. RagService يمرر النص إلى StructureChunker.
3. الـchunker يقسم النص عند الفقرات، ويستخدم عناوين Markdown كأسماء للأقسام.
4. يجمع الفقرات المتجاورة حتى حد افتراضي يقارب 1,100 حرف. عند تقسيم جدول كبير، يكرر صف العناوين قدر الإمكان.
5. يضيف اسم السياسة والقسم إلى نص كل مقطع قبل حساب الـembedding، حتى لا يفقد المقطع سياقه.
6. يرسل OllamaClient كل مقطع إلى نموذج nomic-embed-text عبر /api/embed.
7. يحفظ SQL Server المستند والمقاطع والمتجهات بصيغة JSON.

## ما هو Chunking؟

هو تقسيم مستند كبير إلى مقاطع أصغر، كل مقطع يحمل فكرة أو جزءًا من سياسة. عند السؤال نبحث في المقاطع المناسبة بدل إرسال المستند كاملًا إلى نموذج اللغة. التقسيم عند الفقرات والعناوين يحافظ على المعنى أفضل من تقسيم ثابت كل عدد من الحروف.

النسخة الحالية تعليمية: حد الحجم محسوب بالحروف وليس tokens، ولا يوجد overlap بين المقاطع المتجاورة. لذلك قد تنقسم جملة طويلة أو صف جدول كبير. عند التوسع يمكن استخدام حدود tokens وتداخل بسيط بين المقاطع، أو parser متخصص لفهم الجداول.

## ما هو Embedding؟

هو متجه أرقام يمثل المعنى التقريبي للنص. النصوص المتقاربة في المعنى غالبًا تحصل على متجهات أقرب. عند الفهرسة نخزن متجه كل مقطع. وعند السؤال نحول السؤال إلى متجه باستخدام نموذج embedding نفسه.

يجب استخدام نفس نموذج embedding وقت الفهرسة والبحث. إذا تغير النموذج، أعد فهرسة السياسات لأن أبعاد المتجه أو معناها قد تختلف.

## ماذا يحدث عند السؤال؟

1. Angular ترسل السؤال إلى POST /api/ask مع عدد النتائج topK.
2. nomic-embed-text يحول السؤال إلى متجه.
3. التطبيق يقرأ متجهات المقاطع من SQL Server ويحسب Cosine Similarity بينها وبين متجه السؤال.
4. يختار أعلى المقاطع تشابهًا؛ هذا هو Retrieval.
5. يضع المقاطع المختارة في سياق مع اسم السياسة والقسم ومعرف المقطع.
6. يرسل السؤال والسياق إلى llama3.2:3b عبر /api/generate.
7. يطلب الـprompt من النموذج الإجابة من السياسة فقط ووضع إحالات مثل [Source 1]. ترجع الإجابة ومصادرها إلى Angular.

RAG يجمع بين الاسترجاع الدلالي ونموذج اللغة: الاسترجاع يحدد النص المناسب، والنموذج يصوغ إجابة مفهومة. مصادر الحقيقة هي نصوص السياسة المعروضة مع الإجابة، وليس ذاكرة النموذج.

## كيف تختبر التطبيق؟

1. أضف سياسة الإجازة السنوية من واجهة Angular.
2. اسأل: “كم يوم إجازة لموظف خبرته 3 سنوات؟”
3. تحقق أن الإجابة 21 يومًا وأن المصدر يعرض مقطع سياسة الإجازة.
4. جرّب سؤالًا لا تجيب عنه السياسة. المفترض أن يوضح المساعد أن المعلومة غير موجودة بدل اختراع قاعدة.

## حدود النسخة التعليمية

- لا يوجد تسجيل دخول أو صلاحيات أو عزل بيانات بين الشركات.
- كل المتجهات تقرأ من SQL Server وتحسب المقارنة داخل التطبيق؛ هذا لا يناسب مجموعات ضخمة.
- تخزين vectors في JSON داخل SQL Server اختيار تعليمي. عند التوسع استخدم محركًا يدعم البحث المتجهي.
- لا يوجد overlap أو قياس token-aware في chunking.
- بيانات الدخول في Docker Compose مخصصة للتطوير المحلي فقط.
